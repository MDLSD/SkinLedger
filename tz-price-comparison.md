# ТЗ (этап 2): Сравнение цен между площадками

**Относится к:** SkinLedger, этап 2 (см. бэклог, п. 3 исходного ТЗ).
**Цель:** дать пользователю таблицу сравнения цен на скины между двумя площадками с честным расчётом прибыли (с учётом комиссий), страницу отдельного скина со сводом цен и историей, и поиск лучших связок «где купить → где продать».

Данный раздел не отменяет MVP-леджер, а дополняет продукт новым модулем. Сравнение цен — основная продающая функция платной подписки.

---

## 1. Источник данных

- Цены берутся из внешнего агрегатора по API (провайдер выбирается отдельно; в расчётах — Pricempire, эндпоинты `items/prices` и `comparison`).
- Приложение НЕ обращается к агрегатору в момент открытия страницы пользователем. Цены заранее скачиваются по расписанию (крон) и складываются в собственную БД. Пользователь читает данные из БД.
- Частота обновления: 5–10 минут для таблицы, реже (15–30 минут) для тяжёлых расчётов связок. Настройка задаётся сервером, не пользователем.
- Все цены нормализуются в одну валюту при загрузке; отображение — в валюте пользователя (RUB по умолчанию), пересчёт по сохранённому курсу.
- Отсечка дешёвых предметов делается на стороне API (параметр минимальной цены в запросе) и дополнительно при записи в БД. Порог — не ниже осмысленного для арбитража (ориентир: 50–100 ₽), не 5 ₽.

---

## 2. Модель данных (новые сущности)

Не смешивать с существующей `Platform` (та — справочник комиссий для ручного ввода сделок). Ценовые данные живут в отдельных сущностях.

### 2.1 MarketSource (площадка-источник цен)

| Поле              | Тип            | Примечание                                             |
| ----------------- | -------------- | ------------------------------------------------------ |
| slug              | string         | PK, ключ провайдера: `steam`, `market_csgo`, `buff163` |
| title             | string         | отображаемое название                                  |
| currency          | enum           | валюта площадки: USD/EUR/RUB/CNY                        |
| buy_fee_pct       | decimal        | комиссия покупки, %                                     |
| sell_fee_pct      | decimal        | комиссия продажи, %                                    |
| withdraw_fee_pct  | decimal        | комиссия/потеря при выводе средств, %                  |
| is_active         | boolean        | участвует ли в сравнении                               |

Комиссии заполняются вручную по каждой площадке — именно они превращают «сырой спред» в реальную прибыль. Агрегатор их обычно не отдаёт.

### 2.2 MarketItem (предмет)

| Поле              | Тип            | Примечание                                             |
| ----------------- | -------------- | ------------------------------------------------------ |
| market_hash_name  | string         | PK, канонический ключ склейки цен между площадками     |
| slug              | string         | unique, ЧПУ для публичного URL (см. 7.2)               |
| name              | string         | отображаемое имя                                       |
| weapon            | string, null   | AK-47, AWP, Karambit — для страниц-хабов и крошек      |
| collection        | string, null   | коллекция — для страниц-хабов и крошек                 |
| rarity            | string, null   | редкость                                               |
| exterior          | string, null   | Factory New / Minimal Wear / ...                       |
| is_stattrak       | boolean        |                                                        |
| is_souvenir       | boolean        |                                                        |
| phase             | string, null   | Doppler Phase / Ruby / Sapphire и т.д.                 |
| image_url         | string, null   |                                                        |

### 2.3 PriceQuote (котировка: предмет × площадка, последний срез)

Ровно одна строка на пару (предмет, площадка). Перезаписывается на каждом тике крона.

| Поле              | Тип            | Примечание                                             |
| ----------------- | -------------- | ------------------------------------------------------ |
| market_hash_name  | string         | FK → MarketItem                                        |
| source_slug       | string         | FK → MarketSource                                      |
| price_min         | decimal, null  | минимальная цена (текущий листинг)                     |
| price_order       | decimal, null  | цена ордера покупки (авто-бай), если есть              |
| price_avg_30      | decimal, null  | средняя за 30 дней                                     |
| price_median_30   | decimal, null  | медианная за 30 дней                                   |
| offers_count      | int, null      | количество предложений на площадке                     |
| sales_30d         | int, null      | число продаж за 30 дней (ликвидность)                  |
| fetched_at        | timestamp      | когда котировка получена                               |

PK: (market_hash_name, source_slug). Индекс по (source_slug, fetched_at).

### 2.4 PriceHistory (история для графика)

| Поле              | Тип            | Примечание                                             |
| ----------------- | -------------- | ------------------------------------------------------ |
| market_hash_name  | string         | FK                                                     |
| source_slug       | string         | FK                                                     |
| price             | decimal        | нормализованная цена                                   |
| ts                | timestamp      | момент                                                 |

Растёт быстро — чистить/агрегировать по времени. Индекс (market_hash_name, source_slug, ts).

## 3. Функциональные требования

### 3.1 Таблица сравнения (главный экран модуля)

Модель: пара «площадка закупки → площадка продажи». Пользователь выбирает ровно две площадки.

**Панель настроек (слева):**

- **Сайт для закупки:** выбор площадки + тип цены (см. 3.3).
- **Сайт для продажи:** выбор площадки + тип цены.
- Кнопка «поменять местами» закупку и продажу.
- **Фильтр по цене:** «от» и «до» — отдельно для стороны закупки и для стороны продажи.
- **Фильтр по количеству:** мин./макс. количество предложений (опционально в MVP).
- Кнопка «Сбросить все фильтры».

**Верхняя панель:**

- Автообновление цен (вкл/выкл) с интервалом в секундах.
- Фильтр прибыли: «от» и «до», в % (и/или в валюте).
- Кнопка ручного обновления.

**Таблица (колонки):**

| Колонка              | Содержание                                                        |
| -------------------- | ----------------------------------------------------------------- |
| Избранное / +        | добавить в список / избранное                                     |
| Предмет              | иконка, название, качество, метки StatTrak/Souvenir               |
| Цена (площадка 1)    | цена закупки по выбранному типу цены + число предложений          |
| Цена (площадка 2)    | цена продажи по выбранному типу цены + число предложений          |
| Прибыль              | в валюте И в процентах, с учётом комиссий обеих площадок; цвет     |
| Обновлено            | давность котировки на каждой площадке                             |
| Продажи [30д]        | ликвидность: число продаж за период (по площадкам)                |

- Сортировка по любой колонке (в первую очередь — по прибыли).
- Пагинация или ленивая подгрузка.
- Счётчик «N предметов найдено».
- Чёрный список предметов (исключить из выдачи).

**Расчёт прибыли (обязательная логика):**

```
net_buy  = buy_price  × (1 + buy_fee_pct/100)                    // сколько реально спишут
net_sell = sell_price × (1 − sell_fee_pct/100) × (1 − withdraw_fee_pct/100)  // сколько реально дойдёт
profit   = net_sell − net_buy
profit_pct = profit / net_buy × 100
```

Прибыль всегда считается по чистым суммам, а не по разнице сырых цен. Сортировка таблицы по чистой прибыли, не по сырой цене.

**Фильтр по ликвидности (важно):** предметы с числом продаж ниже порога либо скрывать, либо явно помечать как неликвид. Спред без ликвидности — не прибыль. Порог настраивается; в MVP допустим один общий порог.

### 3.2 Фильтр площадок продаж по ликвидности (расширение 3.1)

- Список площадок с чекбоксами и полем «мин. количество продаж».
- Пресеты периода: 1 / 7 / 14 / 30 дней.
- Позволяет оставить в выдаче только связки, где на площадке продажи предмет реально торгуется N+ раз за период.
- В MVP можно упростить до одного порога по площадке продажи; полную матрицу — в бэклог.

### 3.3 Типы цены

Пользователь выбирает, какая цена берётся за основу расчёта — отдельно для закупки и для продажи. Разные типы дают принципиально разный результат.

Полный набор (как у конкурента): рекомендуемая, ордер покупки (авто-бай), минимальная, средняя за 30 дней, медианная за 30 дней, коридор 50%/7д, коридор 70%/30д.

**Для MVP достаточно трёх, если API их отдаёт:**

- Минимальная цена (текущий листинг).
- Средняя за 30 дней.
- Ордер покупки (авто-бай) — там, где доступно.

Остальные типы — в бэклог, добавляются без изменения архитектуры (это просто выбор поля из PriceQuote).

### 3.4 Страница отдельного скина

Открывается по клику на предмет в таблице.

**Шапка / карточки:**

- Название, изображение, метки.
- Рыночная цена, самая низкая цена, средняя за 7 дней.
- Всего предложений, продаж за 7 дней.
- (Расширение SkinLedger) Карточка «Лучшая связка по профиту» — какая пара площадок даёт максимальную чистую прибыль по этому предмету прямо сейчас: «Купить на X за … → продать на Y за … → прибыль +… (+…%)». На скриншотах конкурента этого нет, это наше отличие.

**Выбор варианта предмета:**

- Список качеств (Factory New … Battle-Scarred), StatTrak, Souvenir — с ценой по каждому.
- Диапазон износа (float), если применимо.

**Сборник цен по площадкам («Предложения на сайтах»):**

- Список всех площадок с текущей ценой, числом предложений, рейтингом площадки (если есть), кнопкой перехода.
- Сортировка (от дорогих к дешёвым и наоборот).

**График истории цен:**

- Наложение нескольких площадок на одном графике (максимум 5 линий).
- Переключатель площадок (какие линии показывать).
- Пресеты периода: 1н / 1м / 3м / 6м / всё время.
- Отображение изменения цены за 24ч / 7д / 30д / 90д (в % и валюте).
- Статистика: мин., макс., средняя за период; число продаж за 24ч/7д/14д/30д.

## 4. Что НЕ входит в этот этап (осознанно)

- Полный набор из 7 типов цены (MVP — 3).
- Полная матрица фильтров по всем площадкам продаж (MVP — один порог).
- Сравнение более двух площадок одновременно в таблице (модель «пара» намеренно; своды по всем площадкам — только на странице скина).
- Алерты по спредам (Telegram) — отдельный пункт бэклога.
- Обход лимитов API через мультиаккаунт/прокси — отвергнуто: нарушает ToS провайдера, ломается в момент роста, ставит весь продукт в зависимость от схемы, которую поставщик вырубает одним движением. Данные — фундамент продукта, фундамент не строят на этом.

## 5. Структура страниц (дополнение к разделу 7 исходного ТЗ)

Принципиально: страницы делятся на **публичную зону** (доступна без входа, индексируется поисковиками) и **приватную** (за авторизацией). Раскладка ниже — не косметика, а требование SEO (раздел 7). Страницы скинов НЕ должны жить под `/app`, иначе поисковый бот их никогда не увидит.

**Публичная зона (индексируется):**

```
/skins                          — каталог: поиск, фильтры, популярное
/skins/[weapon]                 — хаб по оружию (все скины AK-47)
/collections/[collection]       — хаб по коллекции
/skins/[slug]                   — страница скина: своды цен, история, лучшая связка
```

**Приватная зона (за входом, noindex):**

```
/app/prices              — таблица сравнения (пара площадок), рабочий инструмент
/app/spreads             — топ связок по прибыли
/app/deals, /app/settings и т.д. — как в исходном ТЗ
```

Таблица сравнения (3.1) остаётся приватной: это рабочий инструмент под подписку, индексировать там нечего. Страницы скинов (3.4) — публичные: это и есть контент, который приводит поисковый трафик.

## 6. Связь с остальным продуктом

- **Форма сделки:** автоподсказка названия скина теперь может идти из MarketItem (полный каталог), а не только из прошлых сделок. Под полем цены — текущая рыночная цена подсказкой.
- **Дашборд, холд по рынку (п. 2 бэклога):** сделки в статусе `holding` джойнятся к PriceQuote по названию → «Холд сейчас стоит +X% к закупке». Реализуется поверх той же таблицы цен почти бесплатно.
- **Тариф:** бесплатный тир — ограниченный (меньше площадок / задержка обновления / фильтр по цене как у конкурента «до 2$»), платный — снимает лимиты.

## 7. SEO-требования (обязательно, закладывается на этапе проектирования)

Обоснование: страницы скинов генерируются автоматически из данных, за которые мы и так платим. Это десятки тысяч страниц под точные поисковые запросы («AK-47 Redline цена», «Souvenir AWP Dragon Lore сколько стоит»). Самый дешёвый и самый долгий на разгон канал: индексация занимает месяцы, поэтому архитектура закладывается ДО релиза, а не после. Переделка роутинга после запуска ломает уже проиндексированные ссылки.

### 7.1 Рендеринг

- Публичные страницы — серверный рендеринг (SSR) или статическая генерация с ревалидацией (ISR). Клиентский рендеринг цен недопустим: бот должен видеть цены в HTML.
- Ревалидация страницы скина — по времени (ориентир: 15–60 минут), не на каждый запрос.
- Данные берутся из своей БД (PriceQuote), не из внешнего API в момент запроса.

### 7.2 URL

- ЧПУ на латинице, из `market_hash_name`: `ak-47-redline-field-tested`, `souvenir-awp-dragon-lore-factory-new`.
- Slug генерируется один раз и хранится в MarketItem. Менять нельзя — при необходимости менять ставить 301-редирект со старого.
- Никаких uuid и хешей в публичных URL.
- Один предмет = один URL. Варианты качества/StatTrak/Souvenir — отдельные предметы с отдельными URL (у них разные цены и разные запросы).

### 7.3 Метатеги и разметка

- `<title>` и `<meta description>` генерируются из данных: название, текущая цена, число площадок. Шаблон вида «AK-47 | Redline (Field-Tested) — цена на N площадках | SkinLedger».
- Canonical на каждой странице.
- Open Graph и Twitter Card — превью с изображением скина и ценой (важно для расшаривания в Telegram/Twitter, см. каналы продвижения).
- Микроразметка Schema.org: `Product` + `Offer` (или `AggregateOffer`) для цен, `BreadcrumbList` для хлебных крошек.
- Хлебные крошки в интерфейсе и в разметке: Главная → Скины → Оружие → Коллекция → Предмет.

### 7.4 Sitemap и robots

- `sitemap.xml` генерируется автоматически. При десятках тысяч URL — sitemap index с разбивкой (лимит 50 000 URL и 50 МБ на файл).
- В sitemap попадают только страницы с реальными данными (см. 7.6).
- `lastmod` проставляется по времени обновления котировок.
- `robots.txt`: `/app/*` закрыт от индексации, публичная зона открыта. На приватных страницах — `noindex`.

### 7.5 Внутренняя перелинковка

Изолированные страницы индексируются плохо. Нужны связи:

- Страница скина → другие качества того же скина, другие скины коллекции, страница оружия.
- Хабы по оружию и коллекциям — связывают тысячи страниц в структуру.
- Каталог `/skins` со страничной навигацией (не бесконечный скролл без ссылок — бот не докрутит).

### 7.6 Тонкие и пустые страницы

- Предмет без котировок ни на одной площадке или ниже порога отсечки (см. 1) — `noindex`, в sitemap не попадает.
- Массив почти пустых страниц вредит домену в целом, а не только себе.
- Правило: страница индексируется, только если есть цена хотя бы на двух площадках.

### 7.7 Публичное vs платное — решение о том, что скрывать

Ключевой вопрос, требующий явного решения до реализации: **что видит незалогиненный пользователь и поисковый бот.**

- Боту и пользователю должно показываться **одно и то же**. Отдавать боту полный контент, а человеку заглушку — клоакинг, за него санкции.
- Следовательно, всё, что мы индексируем, публично доступно и незалогиненному человеку.
- Рабочая схема: на публичной странице скина открыты **текущие цены и график** (это то, что ищут в поиске, и это есть у всех конкурентов). За подпиской — **инструмент**: таблица сравнения пар, фильтры, расчёт чистой прибыли с комиссиями, лучшие связки, алерты, списки.
- То есть монетизируется не факт знания цены, а скорость и удобство поиска связок. Цены как приманка, инструмент как продукт.

### 7.8 Языковые версии

- На старте — одна языковая версия (русская), английская позже.
- Архитектурно заложить префикс локали в URL (`/ru/...`, `/en/...`) или поддомен, чтобы потом не ломать ссылки.
- При добавлении второй версии — `hreflang` между эквивалентными страницами.

### 7.9 Технические требования

- Core Web Vitals в зелёной зоне. Данные из своей БД, поэтому страница обязана открываться быстро.
- Изображения скинов — оптимизированные, с `alt` по названию предмета.
- Мобильная версия полноценная (основной трафик из поиска — мобильный).

## 8. Влияние на текущий ход разработки

Этап 2 находится в работе (фаза 3 — таблица сравнения). SEO затрагивает не таблицу, а страницу скина (3.4), которая ещё не реализована, — поэтому переделок минимум. Что нужно сделать до начала работы над страницей скина:

1. Добавить `slug`, `weapon`, `collection`, `rarity` в MarketItem и заполнить при сиде каталога.
2. Завести публичный сегмент роутинга отдельно от `/app`.
3. Принять решение по 7.7 (что открыто, что за подпиской) — оно определяет вёрстку страницы скина.

Хабы (`/skins/[weapon]`, `/collections/[...]`), sitemap и микроразметка могут быть добавлены после релиза без переделки — но чем раньше, тем раньше начнётся индексация.
