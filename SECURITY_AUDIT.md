## High

### H1. Список и дашборд фильтруют период по разным датам — агрегаты не сверяются ✔

- **Файл:** `src/lib/deal-query.ts:38-39` (фильтр по `buyDate`) против `src/lib/dashboard.ts:78-81` (по `sellDate`)
- **Тип:** корректность финансовых расчётов
- **Суть:** один и тот же контрол «период» на двух страницах отбирает разные множества сделок.
  Это не погрешность округления — множества просто разные, сверка невозможна в принципе.
- **Воспроизведение.** Сегодня 22.07.2026, период «Месяц» → граница `gte = 2026-06-22`.
  Сделка: куплена 10.02.2026 за 10 000 ₽ (комиссия 0 %), продана 10.07.2026 за 15 000 ₽ (комиссия 13 %).
  ```
  /app/deals?period=month  →  «Под фильтры ничего не подошло»  (0 сделок)
  /app?period=month        →  Чистая прибыль +3 050 ₽, Закрыто сделок: 1
  ```
  Проверено: `15000 × 0.87 − 10000 = 3050.00`.
- **Фикс:** выбрать одну семантику. Для P&L правильна дата закрытия: список фильтровать по `sellDate`
  для закрытых сделок и показывать холд отдельным блоком; либо развести два контрола с явными
  подписями «период покупки» / «период продажи».

### H2. Отсутствующий курс валюты молча превращается в 1:1 ✔

- **Файл:** `src/lib/currency.ts:21` (`if (!rf || !rt) return 1;`), усугубляется `src/lib/rates.ts:19-24`
- **Тип:** корректность финансовых расчётов
- **Суть:** `rates.ts` собирает курсы только из тех валют, что реально пришли в ответе API.
  Если ответ пришёл с `result: "success"`, но без `CNY`, курса не будет, и `fxFactor` вернёт `1` —
  без исключения, без лога, без признака в интерфейсе. Хуже того, `getRates()` в этом случае вернёт
  `live: true`, поэтому даже страница настроек покажет «Обновлено: …» вместо предупреждения.
- **Воспроизведение.** Сделка на Buff163: 500 CNY, комиссия 2.5 %, базовая валюта RUB.
  ```
  курсы полные:  fxFactor(CNY→RUB) = 12.6761  →  500 CNY = 6 496,48 ₽
  курса CNY нет: fxFactor(CNY→RUB) =  1.0000  →  500 CNY =   512,50 ₽
                                            расхождение в 12,7 раза
  ```
  CNY входит в `CURRENCIES`, но не в `BASE_CURRENCIES` — то есть путь CNY→база задействован всегда.
- **Фикс:** `fxFactor` должен возвращать `null` при отсутствующем курсе, вызывающий код — показывать «—»
  и предупреждение вместо числа. В `rates.ts` считать ответ валидным, только если пришли **все**
  `SUPPORTED` валюты, иначе уходить в кэш/фолбэк с `live: false`.

### H3. Нет ни восстановления, ни смены пароля, ни отзыва сессии ✔

- **Файл:** отсутствует как фича; `src/auth.ts:36` (`strategy: "jwt"`), `src/lib/actions/auth.ts:71-72`
- **Тип:** аутентификация
- **Суть:** три отсутствующих контроля, которые вместе дают тупик.
  - Сброса пароля нет — грепом по `forgot`/`reset`/`recover`/`verificationToken` ноль совпадений
    в `src/` и в `schema.prisma`. Забывший пароль пользователь безвозвратно теряет все сделки.
  - Смены пароля нет — `passwordHash` пишется единственный раз, при регистрации.
  - Отзыв сессии невозможен: JWT-стратегия без адаптера означает отсутствие серверных записей сессий.
    Дефолтный `maxAge` — 30 дней (`@auth/core/lib/init.js:38`). Угнанный токен живёт 30 дней, и убрать
    его нельзя ничем, кроме ротации `AUTH_SECRET`, которая разлогинит вообще всех.
- **Итог:** на компрометацию аккаунта у продукта нет ни одного ответа.
- **Фикс (минимальный, закрывает худшую часть):** смена пароля с проверкой текущего + поле
  `sessionsValidFrom DateTime` в `User`; в `jwt`-колбэке класть `iat`, в `session`-колбэке рвать сессию,
  если токен старше `sessionsValidFrom`. Это даёт «выйти на всех устройствах» без перехода на
  database-сессии. Сброс по email — отдельной задачей: одноразовый токен, хеш в БД, TTL 30–60 мин,
  инвалидация всех сессий при использовании.

### H4. Откат импорта ломается на ≥998 сделках — P2029 ✔

### H5. Параметр `to=` с граничной датой роняет список и экспорт ✔

- **Файл:** `src/lib/deal-list.ts:88-92`
- **Тип:** обработка входных данных / доступность
- **Суть:** `validDate()` проверяет `isNaN` **до** `setHours`, а `setHours(23,59,59,999)` толкает
  максимальную дату за границу диапазона `Date` и делает её `Invalid Date` уже после проверки.
  Дальше она уходит в Prisma как `lte`.
- **Воспроизведение:**
  ```
  GET /api/deals/export?period=custom&to=275760-09-13
  GET /app/deals?period=custom&to=275760-09-13
  ```
  Проверено: `new Date("275760-09-13")` проходит `isNaN`, после `setHours` → `Invalid Date`;
  Prisma на таком `where` бросает `PrismaClientValidationError`. Ни `export/route.ts:16`,
  ни `deals/page.tsx:26` не оборачивают вызов в try/catch → 500 на каждый запрос.
  Дашборд не падает (там `range` идёт в чистый JS), но молча теряет фильтр.
- **Фикс:**
  ```ts
  function validDate(s: string): Date | undefined {
    if (!s || !/^\d{4}-\d{2}-\d{2}$/.test(s)) return undefined;
    const d = new Date(`${s}T00:00:00.000Z`);
    if (Number.isNaN(d.getTime())) return undefined;
    const y = d.getUTCFullYear();
    return y >= 2000 && y <= 2100 ? d : undefined;
  }
  // в periodRange: сначала setHours, затем повторная проверка isNaN
  ```

## Medium

### M1. Агрегаты считаются на произвольном подмножестве при >5000 сделок

- **Файл:** `src/app/app/page.tsx:28-32`, `src/lib/deal-query.ts:46-50`
- **Суть:** `take: MAX_ROWS` **без `orderBy`**. Порядок без явной сортировки не гарантирован, а усечение
  происходит до JS-фильтрации по `q` и до сортировки. У пользователя с 6000 сделок дашборд покажет
  прибыль по случайной тысяче — без предупреждения и без признака усечения.
- **Фикс:** считать агрегаты в SQL (`groupBy`/`aggregate`) вместо выгрузки в память; для списка —
  пагинация на уровне БД с детерминированным `orderBy`.

### M2. Колонки списка не сводятся между собой ✔

- **Файл:** `src/components/deals-client.tsx:311`, `:327`
- **Суть:** колонки «Покупка» и «Продажа» показывают `buyPrice × buyFxRate` — цену **за штуку, без
  комиссий**. Колонка «Прибыль» — `profit()`, то есть **всю партию с комиссиями**.
- **Воспроизведение.** `quantity = 10`, куплено по 1 000 ₽/шт (комиссия 0 %), продано по 1 200 ₽/шт (13 %):
  ```
  Скин          Покупка   Продажа   Прибыль   Маржа
  AWP | … ×10   1 000 ₽   1 200 ₽   +440 ₽    4,4 %
  ```
  Наивная проверка `1200 − 1000 = 200` против `+440` в таблице. При комиссии 20 % та же строка дала бы
  убыток при «растущих» ценах в колонках. Маркер `×10` есть (`:299-301`), но он не объясняет,
  что две денежные колонки живут в другом масштабе, чем третья.
- **Фикс:** показывать в колонках `buyCostBase(deal)` / `sellRevenueBase(deal)`, а цену за штуку выносить
  второй строкой рядом с площадкой и датой — место там уже есть.

### M3. «Средняя маржа» — взвешенная по себестоимости, а не средняя ✔

- **Файл:** `src/lib/dashboard.ts:87`
- **Суть:** `avgMargin = netProfit / totalCost × 100` — это ROI портфеля. Подпись «Средняя маржа»
  и колонка «Маржа» в списке заставляют ждать среднее арифметическое.
- **Воспроизведение.** Сделка A (себестоимость 100 000 ₽, прибыль +1 000 ₽ → 1 %),
  сделка B (1 000 ₽, +500 ₽ → 50 %). Список показывает `1,0 %` и `50,0 %`, дашборд — **1,5 %**,
  наивное среднее — 25,5 %.
- **Фикс:** формула финансово осмысленна — переименовать в «Рентабельность вложений»;
  либо считать `avg(marginPct)`, если нужна именно средняя.

### M4. Историческая прибыль переписывается задним числом; снимок курса мёртв

- **Файл:** `src/lib/actions/deals.ts:100-112` (сохранение) против `src/lib/deal-query.ts:65,73`
  и `src/app/app/page.tsx:48,51` (пересчёт)
- **Суть:** `buyFxRate`/`sellFxRate` сохраняются на момент сделки, но при чтении игнорируются —
  всё пересчитывается по **текущим** курсам. Закрытая в марте сделка меняет рублёвую прибыль каждый день,
  помесячный график и кумулятивная кривая переписывают прошлое, два скриншота дашборда за разные дни
  не сойдутся. Сохранённые колонки при этом — чистый мёртвый груз.
- **Фикс:** для реализованной прибыли использовать зафиксированный курс сделки; текущие курсы применять
  только к переоценке открытого холда.

### M5. Флаг `Secure` на cookie сессии зависит от заголовка прокси, а не от окружения ✔

- **Файл:** `src/auth.ts:34-39`
- **Суть:** `useSecureCookies` не задан, поэтому вычисляется как `url.protocol === "https:"`
  (`@auth/core/lib/init.js:69`), а `url` при `trustHost: true` собирается из заголовка `x-forwarded-proto`
  (`next-auth/lib/index.js:9-10`). `AUTH_URL`/`NEXTAUTH_URL` не заданы ни в `.env`, ни в `.env.example`,
  ни в `DEPLOY.md`, значит переопределения из env нет (`next-auth/lib/env.js:6-11`).
  Если TLS терминирует nginx, не выставляющий `x-forwarded-proto: https`, приложение выдаст
  session-cookie **без `Secure` и без префикса `__Host-`** на csrf-токене.
- **Фикс:**
  ```ts
  NextAuth({
    trustHost: true,
    useSecureCookies: process.env.NODE_ENV === "production",
    session: { strategy: "jwt", maxAge: 7 * 24 * 60 * 60 },
    // …
  ```
  плюс `AUTH_URL` в `.env.example` и в чек-лист деплоя — он заодно снимает доверие к заголовку `Host`
  при `trustHost: true` (сейчас `Host: evil.com` подменяет базовый URL для callback/redirect).
  Сократить `maxAge`: при отсутствующем отзыве сессий (H3) 30 дней слишком долго.

### M6. CSP с `'unsafe-inline'` в `script-src`

- **Файл:** `next.config.ts:11`
- **Суть:** комментарий на `:5-7` объясняет это бутстрап-скриптами Next, и это правда для CSP без nonce,
  но следствие — CSP перестаёт быть защитой от XSS. Остальные директивы (`object-src 'none'`, `base-uri`,
  `form-action`) полезны, но главный слой выключен. Самого XSS-вектора в коде нет: React экранирует вывод,
  `dangerouslySetInnerHTML` не встречается — CSP нужен как второй рубеж.
- **Фикс:** nonce-based CSP через middleware (Next 16 поддерживает): nonce на запрос,
  `script-src 'self' 'nonce-{n}' 'strict-dynamic'`. Требует `middleware.ts`, которого сейчас нет.
  Если неоправданно на текущем этапе — зафиксировать как осознанный техдолг.

### M10. Цены и количество без верхней границы ✔

- **Файл:** `src/lib/validation.ts:33-34`, `:52-55`
- **Суть:** проверено на zod 4.4.3 — `"1e400"`, `"Infinity"`, `"NaN"` отклоняются (в zod 4 `z.number()`
  финитен по умолчанию), но **`"1e308"` проходит** как цена, а **`"999999999999"`** — как количество.
  Дальше `buyCostBase` → `Infinity`, и все агрегаты дашборда становятся `∞`/`NaN`. Данные свои,
  но пишутся в БД и необратимо отравляют аналитику пользователя.
  Побочно: `z.coerce.number()` принимает hex — `"0x10"` → `16`.
- **Фикс:**
  ```ts
  const requiredPrice = (msg: string) =>
    z.coerce.number({ error: msg }).positive(msg).max(1e9, "Слишком большая сумма");
  quantity: z.coerce.number(…).int(…).min(1, …).max(100_000, "Слишком большое количество"),
  ```

### M11. Даты сделок без диапазона ✔

- **Файл:** `src/lib/validation.ts:63`, `:72`
- **Суть:** `z.coerce.date()` без границ. Проверено: `"0001-01-01"`, `"9999-12-31"`, `"+275760-09-13"` —

- **Фикс:**

  const dealDate = z.coerce.date({ error: "Укажите дату" })
    .min(new Date("2010-01-01"), "Дата слишком ранняя")
